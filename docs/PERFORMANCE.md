# Drag-overhead microbenchmark

This measures editor work generated by pointer movement, **not FPS, latency, or an end-to-end speed multiplier**.

## Fixture and method

- Local Chromium via Playwright, 1440×900 viewport.
- The same in-memory Markdown note and one floating paragraph.
- Real CodeMirror state/view/history; mocked Obsidian host and renderer.
- Wait for initial rendering and observers, then reset the transaction counter.
- Start from the object's move grip, emit 120 pointer moves, release, and wait 60 ms.
- Count CodeMirror transactions using `EditorView.updateListener`. The UI regression additionally asserts zero transactions before release and checks that content is unchanged.

## Observed run

| Work generated by one gesture | v0.2 baseline | v0.3 worktree |
| --- | ---: | ---: |
| Input pointer moves | 120 | 120 |
| Editor transactions before release | 120 | 0 |
| Editor transactions including release | 120 | 1 |

The baseline implementation is commit `1bd29e057a88e0d30bda7141a15da02a25fe4197`, with test-only counting instrumentation added. Raw observations are `qa/performance-baseline.json` and `qa/performance-current.json`.

The new gesture path previews directly in the DOM at most once per animation frame, then commits geometry at release. A separate height-observer adjustment can add another transaction when text actually reflows. Selection and content-edit transactions remain legitimate and are not suppressed.

Wall-clock durations in the raw files are dominated by Playwright's input pacing. They are deliberately **not** interpreted as improved frame time or app speed. This is a single-fixture deterministic work-count check, not a statistically representative performance study, large-vault benchmark, or test inside the actual Obsidian application.

## Reproduce current implementation

```sh
npm ci
npm exec -- playwright install chromium
npm run benchmark
# Optional existing browser:
CHROMIUM_PATH=/path/to/chromium npm run benchmark
# Optional result path:
BENCH_OUTPUT=/tmp/drag-count.json npm run benchmark
```

The script writes the result file and prints its compact summary. For the v0.2 baseline, use the commit above with the same test counter and benchmark script; production files were unchanged during that baseline run.
